# Rig run sheet - 2026-07-28, commit 438cb93

First rig run after the cross-worker record-loss fix. Prepared, not executed.

## Why this run is worth its money

Every previous rig figure for a query whose large batches crossed a worker boundary
was measured on a pipeline that was silently dropping records. `b791306` fixed that:
a data batch above the send-credit window used to be unsendable and was discarded
without an error. So this is the first run where the throughput numbers and the
correctness premise describe the same engine.

## What to expect, and what would be a surprise

- **q0** is stateless with modest batches, so the fix cannot have touched it. A move
  here is provision variance, not code. It is the control.
- **q12** matched its gate at 184,767 rows before and after the fix, so it was never
  losing records either. Its numbers should be comparable to the last run.
- A **failed job** would be new. `89465dd` made a rejected send fail its task instead
  of returning a discarded `false`. That is deliberate, but it means a latent wire
  problem now surfaces as a dead job rather than a quietly short stream. The laptop's
  914 SQL tests and the full par=4 gate exercise the multi-worker path without
  failing, so this is not expected - only unfamiliar.

## Deliberately out of scope

- **q5 on the rig.** Its prior numbers were measured while its top-N received about
  30% of its input, so there is nothing valid to compare against. If it is run, it is
  a first baseline and must be labelled as one.
- **Chunking overhead as an A/B.** The chunk branch fires only above the credit
  window, so batches that previously succeeded take a byte-identical path plus one
  integer comparison. There is no "before" for the batches that changed behaviour -
  they were dropped. A same-provision A/B would be measuring the comparison.

## Gotchas already paid for once

1. Broker node: Zookeeper AND Kafka both `network_mode: host`. A host-networked Kafka
   cannot reach a bridge-networked Zookeeper on localhost:2181.
2. Engine node: pull `flink:2.2.0-scala_2.12-java21`. The java17 image rejects the jar
   (class file 65).
3. Run the sampler ON the engine node. Public-internet RTT folds into the 500ms slope
   window otherwise.
4. A leftover job from a failed run holds all 16 slots and the next submit fails with
   "insufficient free slots". `teardown_stack` runs on the failure path for this.
5. clink job ids are INTEGERS. Grepping for Flink's hex shape reports a successful
   submit as failed - `cloud/job_id.py` exists for this.
6. `clink_submit_sql` runs from the LAPTOP. The runtime image ships `clink_node` and
   the `clink` CLI, not the submit tool.
